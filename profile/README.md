<p>用一套指标评所有场景，是住宅代理评测最常见的失误。登录看的是验证码弹不弹、首屏多快；订阅看的是支付前后出口有没有漂移；脚本调用看的是成功率和限流比例。三件事的成败条件不一样，用同一把尺子量，结论就会失真。这篇按场景拆评测方法，每个场景给出采样方式、观察指标和判读标准，最后合成一张评分卡。</p>

<h2>一、评测前把变量固定住：账号、时段、出口</h2>
<p>评测最怕变量乱动。同一天换了账号、换了浏览器、又换了出口，最后得出「这条线不行」，其实可能是新账号本身处在观察期。开测之前把能固定的都固定下来。</p>

<h3>账号要选成熟的</h3>
<p>用已经稳定使用一个月以上的账号做测试，避免新号的观察期干扰。如果一定要测新号，就和成熟号分开记录，不要混在一张表里对比。</p>

<h3>时段要覆盖高峰</h3>
<p>至少包含工作日下午、晚高峰 20:00 至 22:00、以及一个非工作日上午。三个时段的差异往往比不同供应商之间的差异还大，只测一个时段容易得出偶然结论。</p>

<h3>出口只换一个变量</h3>
<p>评测多条线时，一次只换出口，浏览器配置、设备、网络接入方式都保持不变。想同时比较出口和浏览器环境，就分两轮做，别在一轮里改两样。</p>

<h2>二、登录场景：验证码频率与首屏加载</h2>
<p>登录是三条链路里最敏感的一环，因为它同时受出口身份、请求环境和账号历史影响。评测时不要只记「能不能登进去」，要记「登进去费了多少步」。</p>
<img src="/tp.png" alt="登录测试记录表按天统计验证码次数与首屏加载耗时">
<p>建议用一个固定表格记录：日期、时段、是否弹验证码、验证码类型（图形、短信、邮件）、首屏加载秒数、是否登录成功。七天下来，验证码的分布形态比单次结果有信息量——如果只在前两天弹，多半是新环境适应期；如果每天弹，说明出口或环境有持续性问题。</p>

<h3>首屏时间怎么量</h3>
<p>用浏览器开发者工具的网络面板，看主文档和关键接口的完成时间，取三次的中位数。别用秒表掐，误差太大。首屏超过三秒时，先排除本地网络和 DNS，再归因到出口。</p>

<h3>验证码类型比次数更说明问题</h3>
<p>图形验证码通常是最轻的一档，短信和邮件验证意味着平台在确认身份归属。评测表里把类型分开记，能看出这条线是「轻微提醒」还是「重点观察」。</p>

<h2>三、订阅场景：支付前后出口是否一致</h2>
<p>订阅环节的核心不是速度，是一致性。支付页打开时是一个出口，支付回调时换成另一个出口，是很多失败的根源。评测方法很朴素：支付前查一次出口，支付完成后再查一次，两次必须一致。</p>

<h3>支付页可达性单独记</h3>
<p>有的线路能正常对话但支付页打不开，或者打开后样式错乱。这类问题与出口地区、DNS 解析有关，评测时单独列一栏「支付页是否完整加载」，不要和「能否支付成功」混为一谈。</p>

<h3>出口漂移的检测</h3>
<p>如果用的是池化线路，出口可能在请求之间轮换。检测方式是连续查十次出口，看结果是否稳定。稳定为一条的适合订阅场景，每次不同的只适合不涉及登录态的任务。</p>

<h3>账单信息与出口地区</h3>
<p>支付时填写的账单地区与出口地区差异过大，容易触发额外验证。评测阶段就把这一点记录下来，作为后续配置的依据，而不是等到真扣款失败才发现。</p>

<h2>四、调用场景：成功率、429 比例与长连接</h2>
<p>脚本调用的评测更接近工程指标。成功率、错误码分布、长连接稳定性三项，基本能刻画一条线的可用程度。</p>

<h3>错误码要分类统计</h3>
<p>把失败拆成连接超时、TLS 失败、429、5xx、4xx 五类。连接类多半是线路问题，429 是频率或额度问题，4xx 多半是参数问题。只看总成功率，会把参数错误算到线路头上。</p>

<h3>429 比例反映的是节流而非质量</h3>
<p>429 出现得多，先看自己的请求节奏，再看是否多个实例共用同一凭据。把并发降下来、加上退避，429 通常会明显下降。这一点不澄清，很容易误判成「这条线被限速了」。</p>

<h3>长连接挂两小时看断连</h3>
<p>用一条长连接持续发送心跳，记录断连次数和重连耗时。断连频繁说明线路或中间设备有超时策略，重连耗时长说明握手环节有问题。这两项对需要常驻的自动化任务很关键。</p>

<h2>五、把三个场景合成一张评分卡</h2>
<p>三个场景的指标不能直接相加，要先归一化再按权重打分。长期账号场景给登录和订阅更高权重，批处理场景给调用成功率更高权重。</p>

<h3>归一化的简单做法</h3>
<p>每个指标设一个基准值和目标值，实测落在两者之间按线性折算成 0 到 100 分。比如验证码次数基准 5 次得 0 分、0 次得 100 分，实测 2 次就是 60 分。做法粗糙但可比。</p>

<p>最终输出不要只有分数，附一句结论：这条线适合长期登录，不适合高并发调用；或者这条线延迟好但订阅环节有漂移风险。评分卡是给决策用的，不是给报表用的。</p>

<h2>常见问答</h2>
<h3>评测要跑多久才有结论？</h3>
<p>答：登录和订阅场景建议连续七天，因为验证码的触发有明显的前几天适应期；调用场景三天足够看出成功率与限流。时间太短容易被单日波动误导。</p>

<h3>用同一个账号测多条线，会不会互相影响？</h3>
<p>答：会。频繁切换出口本身就可能引起额外验证。建议一条线配一个账号，或者按天分段测试，每天只用一条线，减少交叉干扰。</p>

<h3>支付环节不敢实测怎么办？</h3>
<p>答：可以先用最低价档位走一次完整流程，观察支付页可达性与出口一致性，不必等到续费日。重点是验证链路，不是验证金额。</p>

<h3>评分卡里权重怎么定？</h3>
<p>答：按业务失败代价定。登录失败会中断当天工作，权重给高；调用失败有重试兜底，权重可以低一些。权重不同结论会变，所以评分卡要写清适用场景。</p>

<h2>合规提示</h2>
<p>评测应使用自有账号与授权资源，不得使用他人账号、他人支付方式或未经许可的网络资源进行测试。测试过程中产生的数据应按内部规范保存与销毁。</p>
<p>代理服务的使用须遵守目标平台服务条款与所在地法律法规。不得利用评测结果从事伪造身份、冒用信息或干扰平台正常运营的行为。</p>
<p>文中指标与合格线为经验参考，实际应结合自身业务特征调整，价格与性能数据以服务商当期说明为准。</p>
